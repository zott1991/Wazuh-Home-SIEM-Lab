Wazuh Home Cybersecurity Lab
Phase 2 Debrief — Telemetry & Detection
Status: Complete
# 1. Objective
Validate the end-to-end SIEM pipeline by generating a controlled SSH authentication event on Kali and tracing it through journald, the Wazuh Agent, Manager, detection rules, MITRE ATT&CK enrichment, and the Wazuh Dashboard.
# 2. Baseline Validation
Verified Wazuh Indexer, Manager, and Dashboard were running after reboot.
Verified the Kali Wazuh Agent was active and connected to the Manager.
Verified the Host-only network: Kali 192.168.56.101; Wazuh server 192.168.56.102.
Verified Kali's ossec.conf contains a journald collector.
Verified wazuh-logcollector reports: 'Monitoring journal entries.'
# 3. Controlled SSH Test
SSH was started temporarily on Kali. A controlled failed login was generated with the intentionally nonexistent account 'fakeuser' and an incorrect password.
Invalid user fakeuser from 192.168.56.101
pam_unix(sshd:auth): authentication failure
Failed password for invalid user fakeuser from 192.168.56.101
Connection closed by invalid user fakeuser
# 4. Telemetry Pipeline
A separate logger/journald test confirmed that newly created journal events from Kali reach the Wazuh Manager. The complete verified pipeline was:
Kali event → journald → Wazuh Agent/logcollector → Wazuh Manager → decoder → rule → alerts.json/Indexer → Dashboard
# 5. Detection Results
# 6. Dashboard Investigation
Threat Hunting → Events displayed two Rule 5710 hits for kali-attacker. The expanded event exposed the source IP, targeted username, sshd decoder, original full log, severity, rule description, and MITRE ATT&CK mappings. Raw alerts.json also showed Rule 5503, 'PAM: User login failed.'
This demonstrated that Dashboard filters matter: the two Rule 5710 hits were not the complete set of alerts generated by the test.
# 7. Troubleshooting Lessons
An empty search of ossec.log does not prove an event was not collected; ossec.log is primarily a component/status log.
A Dashboard view can omit relevant alerts because of its active filters.
alerts.json provided direct evidence that the Kali SSH events were decoded and alerted.
A simple logger/journald test helped separate general journald collection from SSH-specific detection.
The timestamp in the original log can differ from the Wazuh alert timestamp because processing occurs afterward.
# 8. Phase 2 Result
Phase 2 successfully demonstrated an end-to-end SIEM detection workflow: controlled event generation, endpoint telemetry, agent collection, Manager processing, rule matching, MITRE enrichment, and analyst investigation in the Dashboard.
# 9. Evidence to Retain
Kali journal showing the fakeuser SSH failure.
alerts.json output showing Rules 5710 and 5503 for kali-attacker.
Threat Hunting Dashboard showing the Rule 5710 events.
Expanded event details showing source IP, username, decoder, rule, severity, and MITRE mappings.
# 10. Phase 3 Roadmap
Generate and analyze a successful SSH authentication.
Compare successful, failed, and nonexistent-user authentication events.
Generate repeated controlled authentication failures and examine rule behavior.
Investigate alert frequency/correlation behavior.
Create and validate a custom Wazuh detection rule.
Document the custom detection from event generation through Dashboard investigation.
